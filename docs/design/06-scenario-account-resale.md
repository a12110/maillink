# 06 场景：卖号取码

一个 iCloud 隐私邮箱别名是某个平台账号的登录邮箱。卖家交付"账号 + 密码 + 取码链接"，买家登录时平台把验证码发到别名，买家打开链接自己取码。

## 1. 两种卖法，规则取向相反

| 卖法 | 买家得到什么 | 卖家最怕什么 | 规则取向 |
| --- | --- | --- | --- |
| 共享 / 租号 | 登录权。账号仍归卖家，可能多人共用 | 买家改密码、改邮箱把号拿走；一个链接被多人用 | 最严：只给登录验证码 |
| 买断 | 账号归买家，质保期内可继续收信 | 质保期过了还在用；看到同一别名上其他平台的邮件；看到账单信息 | 质保期内放宽，到期自动失效 |

所以不是一个模板，而是每种卖法一个模板，再按平台各克隆一份。

## 2. 这个场景推动的模型改动

已同步进 `01`、`02`、`04`、`05`：

| 改动 | 原因 |
| --- | --- |
| 新增内置邮件分类 `category` | 很多平台重设密码也是发 6 位码。只看"有没有验证码"会把改密码的码也交出去 |
| 发件人改为候选集合（`From` 头 + `X-ICLOUD-HME` 的 `s=`），任一命中 | 白名单是这个场景的根基，不能押在一个还没用真实邮件验证过的字段上 |
| "首次访问"改为访客点击"开始取码"，所有 `GET` 无副作用 | 链接粘贴进微信、Telegram 时预览机器人会先抓一次，不能让它触发激活 |
| "首个访问者绑定"改为"设备数上限" | 买家换手机、清 Cookie、从微信内置浏览器换到系统浏览器都很常见，严格单设备绑定会制造大量售后 |
| "查看次数"改为按不同邮件计的"取码次数"，加"点击取码"方式 | `code_only` 视图没有详情页，原来的计数方式不成立；点击取码还能留下"谁在什么时候取了哪封"的记录 |
| 链接可换绑收件地址、可重置起始时间 | 售后换号时买家手里的链接不用变 |
| 管理员预览（带逐封 trace，无副作用） | 买家说"收不到码"时要能马上看到原因 |
| `code_only` 可显示登录链接 | 有的平台不发验证码，发的是一次性登录链接 |
| 链接加订单号、给买家看的标题与说明 | 售后按订单号找链接；取件页要能写使用说明和联系方式 |
| 从一封邮件生成规则草稿 | 按平台建白名单时不用手抄发件人和主题 |

## 3. 推荐配置

### 3.1 白名单的三档严格度

| 档 | allow 条件 | 适用 |
| --- | --- | --- |
| L1 | 发件人域名 | 买断 |
| L2 | 发件人域名 + `category = verification` | 默认 |
| L3 | L2 + 主题匹配已知的登录验证码主题 | 共享号、高价值号 |

`category` 靠关键词表，词表没覆盖的语言会把高危邮件漏判成 `verification`。L3 用主题白名单兜住这种情况：主题不是已知的登录邮件就不显示。主题模式不要手写，在"全部邮件"里找到一封真实的登录验证码邮件，用"以此邮件创建规则"生成。

### 3.2 模板 A：共享 / 租号（L2）

```json
{
  "time": { "window_minutes": 15, "since": { "type": "first_access", "lookback_minutes": 5 } },
  "filter": {
    "mode": "whitelist",
    "rules": [
      { "id": "allow-login", "name": "本平台的验证码", "enabled": true, "effect": "allow",
        "when": { "all": [
          { "field": "sender.domain", "op": "domain_is", "value": ["openai.com"] },
          { "field": "category", "op": "eq", "value": "verification" }
        ] } },
      { "id": "deny-custom", "name": "自定义屏蔽词", "enabled": true, "effect": "deny",
        "when": { "field": "content", "op": "contains", "value": ["更换邮箱", "change your email"] } }
    ]
  },
  "present": {
    "view": "code_only", "extract": ["code"],
    "sender": "name", "recipient": "full", "snippet": false,
    "links": "strip", "remote_images": "block", "attachments": "hidden", "redact": []
  },
  "limits": { "max_mails": 3 }
}
```

几个取值的理由：

- `since = first_access`：链接往往提前批量生成放进库存，卖出去才被打开。按创建时间算会让买家看到库存期间的邮件。
- `lookback_minutes = 5`：买家常常先点"发送验证码"再打开链接。
- `window_minutes = 15`：验证码本来就只有几分钟有效，旧的留着只会让人填错。
- `recipient = full`：别名就是登录邮箱，买家本来就知道，显示出来还能帮他核对是不是填对了。
- `max_mails = 3`：连点几次"重新发送"时能看到最新几封，又不至于成为历史记录。

### 3.3 模板 B：买断（质保期内收信）

与模板 A 的差别：

- `time`：`since = first_access`、`lookback_minutes = 10`，不设滚动窗口。
- `filter`：L1，只限发件人域名；可加一条 deny `category = billing`。
- `present`：`view = text`，`links = keep`（买家需要点确认链接把邮箱换成自己的）。
- 链接：`expire_after_first_access_sec` = 质保期。

### 3.4 模板 C：发登录链接的平台

在模板 A 基础上：`"extract": ["code", "login_link"]`，`"links": { "allow_domains": ["<平台域名>"] }`。登录链接等于一次完整登录，只给确实不发验证码的平台用。

### 3.5 链接访问约束的建议值

| 项 | 共享 / 租号 | 买断 |
| --- | --- | --- |
| 过期 | 首次访问后 = 租期 | 首次访问后 = 质保期 |
| 设备数上限 | 2 | 3 |
| 取码方式 | 点击取码 | 自动显示 |
| 每日取码上限 | 10–20 | 不限 |
| 人机验证 | 建议开 | 可选 |
| 访问口令 | 可选（口令和链接分开发） | 不用 |

## 4. 平台预设

预设不是特殊代码，只是"新建规则组"时的表单默认值，存成前端的一份数据文件。每条包含：平台名、发件人域名、可选的主题模式与验证码正则。

起步清单（只填可注册域名，`domain_is` 会自动覆盖其子域名）：

| 平台 | 发件人域名 |
| --- | --- |
| OpenAI | `openai.com` |
| Anthropic | `anthropic.com` |
| Google | `google.com` |
| Apple | `apple.com` |
| Microsoft | `microsoft.com` |
| Netflix | `netflix.com` |
| Steam | `steampowered.com` |
| Discord | `discord.com` |
| Spotify | `spotify.com` |

这些是凭常识填的初始值，**没有用真实邮件核对过**。每个平台上线前都要拿一封真实的登录邮件在测试器里跑一遍，尤其要确认经 iCloud 转发后发件人候选里确实有这个域名。主题模式与验证码正则一律从真实邮件生成，预设里先留空。

## 5. 链接生命周期

| 事件 | 操作 | 效果 |
| --- | --- | --- |
| 备货 | 多选收件地址 → 选平台规则组 → 批量生成（一址一链）→ 按模板导出 | 链接处于未激活状态，不计时 |
| 发货 | 把导出的行交给买家或发卡平台 | — |
| 买家首次使用 | 买家点"开始取码" | 登记设备、开始计时、确定时间下界 |
| 续费 | 批量延长有效期 | — |
| 换设备被拦 | 重置设备 | 清空该链接的设备记录 |
| 售后换号 | 换绑收件地址，勾选重置起始时间 | 链接地址不变；买家看不到新号上换绑之前的邮件 |
| 退款 / 违规 | 撤销 | 立即失效 |
| 同一个号再卖 | 新建链接 | 新买家的时间下界从他自己首次访问算起。创建时若该地址已有生效链接，给出提示（共享号是正常情况，所以只提示不阻止） |
| 链接外泄 | 重置 token | 旧地址失效，把新地址发给买家 |

库存状态（在库 / 已售 / 售后中）本系统不建模，用收件地址的标签和链接的订单号来管。

## 6. 买家取件页

买家不是技术人员，页面要回答四个问题：这是哪个号的、现在该干什么、码是多少、出问题找谁。

- 顶部：卖家设的标题（如"ChatGPT 共享号"）与登录邮箱。
- 未激活时：卖家说明 + "开始取码"按钮。
- 等待时：明确写"去登录页点发送验证码，一般 10–60 秒内到达"，带自动刷新的动态指示。
- 到达时：大号验证码、复制按钮、来源、"32 秒前"。超过 10 分钟的弱化并标"可能已过期"。
- 点击取码方式：先显示"有 1 封新邮件"，点了才出验证码，并提示今日剩余次数。
- 底部：卖家留的说明与联系方式（纯文本，不渲染 HTML）。
- 收不到码时的自查提示：确认登录用的是页面上这个邮箱；等一分钟再点一次发送；仍然没有就联系卖家。
- 一段时间没有操作或页面切到后台时停止自动刷新，给"继续刷新"按钮。

## 7. 边界情况

| 情况 | 处理 |
| --- | --- |
| 链接被聊天软件的预览机器人抓取 | `GET` 无副作用，激活必须点按钮；页面不输出可供预览的邮件内容，带 `noindex` |
| 卖家自己想测一下链接 | 用后台"预览"，不占设备、不计次、不激活 |
| 买家先点发送，后开链接 | `lookback_minutes` |
| 邮件经 iCloud 转发有延迟 | 页面写明等待时间；自动刷新 |
| 重设密码发的也是 6 位码 | `category` 判为 `password_reset`；高价值号用 L3 主题白名单 |
| 账号语言不是中英日 | 关键词表可能没覆盖。把账号语言设成已验证过的语言，或用 L3 |
| 平台换了邮件模板或发件域名 | 买家收不到码。后台预览里能看到"未命中 allow"，改预设后对所有引用它的链接立即生效 |
| 验证码被误提取（年份、金额、订单号） | 提取要求紧邻关键词；仍不准就给该平台规则组设 `code_regex` |
| 验证码带空格或连字符、是字母数字混合、只出现在主题里 | 提取规则已覆盖，见 02 §4.6 |
| 同一个别名注册了多个平台 | 每个平台一个规则组、一个链接，互相看不到 |
| 共享号多个买家 | 每人一个链接。同一封验证码所有人都能看到，系统分不出是谁触发的；取码记录能看出谁取了 |
| 买家换设备 / 清 Cookie / 换浏览器 | 设备数上限留余量；超了由卖家重置 |
| 链接被转卖或多人共用 | 设备数上限 + 每日取码上限；链接列表对设备数、国家数异常的行做标记 |
| 买家说收不到码 | 后台预览：逐封显示可见与否及原因 |
| 改规则组影响已售链接 | 保存前显示影响数量；大改先克隆再逐步切换 |
| temp_email 的定时清理删了邮件 | 确认其保留期长于规则里的时间窗口 |
| 高危邮件到达已售邮箱（有人在尝试改密码） | 二期：定时扫描有生效链接的地址，把 `password_reset / email_change / security_change` 类邮件列为风险提醒 |

## 8. 批量与自动化

- 导入：每行"地址, 平台, 备注"，平台列映射成标签。
- 批量生成：按标签筛出某平台的地址 → 选对应规则组与访问约束 → 一址一链。
- 导出：CSV，或按行模板输出，例如 `{address}----{link}`，直接贴进发卡平台的卡密库存。
- 二期：API 令牌，让发卡平台或自建商城在下单时调用接口建链接（README 的 D9）。

## 9. 请求量

取件页是整个系统请求量的主要来源。一个一直开着、每 10 秒刷新一次的页面是每天 8,640 次请求；Workers Free 每天 10 万次，只够十来个这样的页面。所以：

- 页面在后台时暂停刷新；最后一次操作后 5 分钟自动暂停。一次正常取码大约 30 次请求。
- 轮询接口在没有新邮件时不写库：`last_access_at` 只在"开始取码"和交付邮件时更新。
- 轮询只查 `id > after_id` 的候选，没有新邮件时不触碰 `mail_index` 和正文。

## 10. 解决不了的

- 平台对登录和敏感操作用**完全相同**的邮件时，规则分不出来。
- 平台允许已登录用户只凭"发到新邮箱的验证码"就换绑邮箱时，旧邮箱收不到任何东西，本系统无从拦截。
- 链接共享只能限制和发现，不能杜绝：买家可以把取到的码转发给别人。
- 共享号里无法把一封验证码归属到某个买家。

## 11. 需要的测试样本

每个要卖的平台至少各一封，经 iCloud 隐私邮箱转发后的真实邮件（脱敏）：登录验证码、重设密码、更换邮箱、账单。放进 `test/fixtures/`，分类器和各平台预设的单测都跑在它们上面。
